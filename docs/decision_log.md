# Журнал инженерных решений

Дата: 18 октября 2026 года. Рабочая папка `D:\SberTech`.

1. Источники — два предоставленных train CSV, markdown с конкурсным заданием и встроенным scorer, проект backend-ТЗ DOCX и mission-текст. Документы изучены как исходные материалы; объём реализации подтверждён пользователем отдельно: модель, прогноз и API. Внешние данные и платные API не использовались.
2. Локальный компьютер имеет около 15,8 GiB RAM и Ryzen 7 5700. Обучение последовательное, LightGBM использует четыре потока. GPU для решения не требуется; фактическое наличие GPU не проверялось. Docker Desktop был установлен, движок запущен для контейнерной проверки.
3. Для submission выбран полный декартов каталог 11 × 799, включая 12 пар без продаж. Для таких пар строятся общие признаки и прогноз той же глобальной модели; скрытой подстановки нулей вместо отсутствующего прогноза нет. Каталог считается заданным справочником задачи и используется одинаково на всех срезах.
4. Sales агрегируется суммой quantity по дате, складу и артикулу. 521 693 строки повторяют дневной ключ; автоматически удалять их нельзя. Каждый календарный день на глобальном уровне присутствует. Отсутствующие продажи внутри ряда трактуются как нулевые по допущению о событийной выгрузке. Это допущение требует подтверждения владельцем данных.
5. Stock не суммируется. При подготовке исходной обучающей истории удаляются 57 отрицательных измерений; после этого целиком исключаются ключи, у которых осталось несколько разных stock. Полностью одинаковые дубли удаляются. Неизвестный остаток остаётся NaN, его покрытие и давность входят в признаки. Скрипт `prepare_api_inputs.py` делает ту же очистку явно; API самостоятельно не исправляет отрицательные или конфликтующие данные и отвечает 422.
6. Минимальная история API — 180 календарных дней включительно. При более длинном входе используются все данные для long_mean и последние 180 дней для оконных признаков. Будущие относительно max(sales.date) остатки не используются. Качество при сокращённой истории проверяется отдельно, совпадение offline/API утверждается только для одинаковых входов.
7. Обязательные колонки sales соответствуют фактическим 12 колонкам train; cost_price и volume_weight отсутствуют в train и не требуются. Stock поддерживает article и char_article; конфликт двух алиасов отклоняется.
8. Оптимизация использует семантику встроенного scorer: (0,0) исключены из среднего SMAPE внутри ряда. Текстовая версия считается отдельно. Локальный minmax относительно last-value — диагностический критерий, а не гарантированный конкурсный балл при ранговой нормализации.
9. Портфель задан заранее: шесть простых моделей, LightGBM L2 и Tweedie, три фиксированных порога 0/0,25/0,5. На двух первых 64-дневных срезах выбрана архитектура; файл `selection_frozen.json` записан до оценки последнего среза. Последние 64 дня не использовались для выбора порога, objective, числа деревьев или признаков. Это единичный holdout, а не доказательство превосходства во всех будущих периодах.
10. Все прямые обучающие примеры имеют 180 дней истории и полностью известные 64 дня меток до cutoff. Для ограничения размера данных используются origins через 35 дней и фиксированные горизонты 1,7,14,21,28,42,56,64. Модель получает номер горизонта и календарь; предыдущие прогнозы не подставляются обратно в историю. Метрики считаются по всем 64 горизонтам и полному каталогу.
11. Категории, цены и скидки не использованы в этой версии: достаточно проверенного компактного набора истории, ID, агрегатов и остатков. category_lvl_3 почти полностью пустая. Никаких будущих финансовых значений или восстановления анонимизированной шкалы нет. CatBoost, нейросети и сложный ансамбль не тестировались; преимущества им не приписываются.
12. В API один worker, последний успешный прогноз в RAM, новый успешный POST заменяет кэш атомарно. Конкурирующий POST получает 409; GET удерживает прежний snapshot до замены. До первого POST — 409; неизвестный ID входного CSV — 422; неизвестный GET-фильтр — 404. После перезапуска кэш пуст.

Точные результаты, ограничения и проверка контейнера записаны в отчётах. При любых изменениях модели нужно заново выполнить parity и контейнерный прогон.
