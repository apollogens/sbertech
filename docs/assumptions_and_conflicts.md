# Допущения и конфликты источников

## Приоритет источников

Пользователь явно заказал полное решение с моделью, прогнозом и API в `D:\SberTech`. Официальные требования берутся из markdown хакатона; рекомендации DOCX используются как инженерные варианты. Приложенный mission-текст не является доказательством метрик, производительности или готовности. Все утверждения об успешных проверках должны опираться на фактические результаты.

## SMAPE: текст против исполняемого scorer

Markdown §5.2 считает ошибку для факта=0 и прогноза=0 равной нулю. Но функция `smape_series` в §9 исключает эти точки из знаменателя среднего (`mask = denominator > 0`). Для ряда truth=[0,1], pred=[0,0] текстовая формула даёт 100%, встроенный код — 200%. Для полностью нулевого ряда встроенный код возвращает 0.

Решение: при выборе модели использовать точную семантику встроенного scorer. Дополнительно показывать `smape_include_zero_zero` как отдельную диагностическую метрику. Оригинальный Python-блок извлечён без изменения в `scripts/official_score.py`; `src/metrics.py` проверен относительно него на разреженных массивах, полностью нулевых рядах, NaN и отрицательных прогнозах. Проверка `python -m pytest tests/test_metrics.py -q`: 13 passed.

## Нормализация и итоговый рейтинг

§5.3 задаёт minmax по baseline, но §9 сообщает, что ожидается ранговая оценка. Итоговый конкурсный rank невозможно восстановить по одной команде: он зависит от состава участников и других прогнозов. Локально фиксируется last-value baseline на том же временном окне и используется диагностический minmax score. Все пять сырых метрик обязательны, даже если clipping скрывает ухудшение отдельной метрики.

При baseline_metric=0 оригинальный код возвращает 0 для model_metric=0, иначе 1. Для WAPE полностью нулевая истинная выборка даёт 0 даже при положительном прогнозе. Bias исключает серии с нулевым средним truth. Эти особенности сохранены ради воспроизводимости, а не интерпретируются как отсутствие ошибки прогноза.

Оригинальный rank использует `np.argsort` и не усредняет равные ранги. Для равных метрик порядок кандидатов может влиять на результат. Ранговые диагностические сравнения допустимы только с зафиксированным списком кандидатов.

## Полный каталог против наблюдаемых пар

Markdown §4 требует одновременно все встречавшиеся пары и ровно 562 496 строк (11 × 799 × 64). По аудиту sales содержит 8 777 наблюдаемых пар, полный каталог — 8 789, разница 12. Приоритет отдан явному размеру и константам scorer: итоговый файл содержит полный декартов каталог. Ненаблюдавшиеся пары требуют описанного fallback по доступной истории / иерархии; нельзя молча считать отсутствие модельного прогноза успехом.

## Реальные схемы CSV

В реальном sales отсутствуют заявленные `cost_price` и `volume_weight`. В реальном stock артикул называется `article`, тогда как markdown ожидает `char_article`. Pipeline должен принимать фактическую схему и нормализовать оба варианта имени артикула stock. Отсутствующие необязательные финансовые поля не должны блокировать исходную выборку. Если одновременно присутствуют два варианта имени, их конфликт следует отклонять, а не выбирать произвольно.

## Отрицательные остатки и отсутствующие записи

Исходный stock содержит 57 отрицательных значений (минимум −2), хотя backend-шаблон отклоняет stock<0. Подготовка обучающих данных должна явно регистрировать эти аномалии и выбранную обработку. Строгий API может отклонять отрицательный stock; в этом случае для полного исходного файла необходима явная очистка перед загрузкой. Различие должно быть описано в README и проверках.

Отсутствие строки sales интерпретируется в дневной панели как нулевая наблюдаемая продажа. Это рабочее допущение для событийной выгрузки: оно не доказывает нулевой скрытый спрос. Отсутствующий stock не равен нулевому stock; требуется отдельная маска наблюдаемости. Будущие реальные stock и финансовые показатели недоступны прогнозу и не допускаются в признаки валидации.

## Горизонт и глубина истории

Конец предоставленного sales — 2026-07-31; официальный прогноз покрывает 2026-08-01–2026-10-03 независимо от текущей даты компьютера. API должен брать origin из max(sales.date), а не max(stock.date). 180 календарных дней истории трактуются включительно: `(max_date - min_date).days + 1 >= 180`. Пример валидатора в markdown проверяет разность без +1 и потому требует фактически 181 день; буквальное требование «не менее 180 дней» имеет приоритет перед примером.

## Границы исходного аудита

Первичный отчёт `reports/data_audit.md` фиксирует 1 492 370 строк sales и 6 153 988 stock, 943 и 962 даты соответственно. Расширенный аудит и фактические проверки завершены позднее: `detailed_audit.json`, `independent_review.md`, `integration_review.md`, `container_benchmark.json` и `final_verification.md`.

Отрицательные stock удаляются до разрешения дублей. После этого все конфликтующие ключи целиком исключаются, одинаковые дубли удаляются. API отвечает 422 на сырой неоднозначный stock; для предоставленных файлов нужен явный `scripts/prepare_api_inputs.py`. Категории sales обязательны как колонки фактической схемы, но могут содержать пустые значения; cost_price и volume_weight не требуются.
