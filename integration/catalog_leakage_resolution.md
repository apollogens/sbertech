# Каталог по времени наблюдения: исправление экспериментального контура

Дата проверки: 19 октября 2026. Реализованы `integration/catalog_policy.py` и шесть исполнимых проверок. Исходные `src/data.py`, `src/features.py`, действующие веса и serving не изменены. Этот документ описывает контракт признаков; сам по себе он не подтверждает качество повторно обученных моделей.

## Подтверждённое происхождение ID

Скрипт `integration/catalog_audit/verify_provenance.py` повторно прочитал исходные sales и stock CSV (1 492 370 и 6 153 988 строк), вычислил первые даты присутствия warehouse/article и SHA-256 исходников. Результат совпал с предыдущим аудитом для всех отдельных ID. Полные хеши и пути находятся в `catalog_audit/result.json`, новые даты — в `catalog_audit/first_observed.csv`. Первое наблюдение строки, включая строку с нулевой quantity, определяет доступность ID; первый положительный спрос для этого не используется. Это дата наблюдения в экспорте, не доказательство даты ввода товара в бизнесе.

На пяти внешних origins известны соответственно 788, 792, 793, 799, 799 товаров и все 11 складов; число допустимых пар 8668, 8712, 8723, 8789, 8789. На самом раннем внутреннем origin 2024-06-28 sales содержит только 560 товаров и 10 складов: допустимы 5600 пар, а не 8789. Таблица `catalog_audit/origins.csv` охватывает 25 различных внешних/внутренних дат.

Выбрана консервативная **sales-only** политика появления ID, согласованная с источником исходного каталога. На пяти внешних origins наборы sales и sales∪stock совпадают. На внутренних origins совпадение отсутствует: на 2024-06-28 stock уже содержит ещё один склад и 49 товаров, которых нет в sales. Таким образом, sales-only сознательно не использует stock-only ID до первого появления в sales; это воспроизводимая модельная политика, а не утверждение, что такие ID объективно неизвестны. Числа stock-only по всем датам приведены в таблице. Категории и их возможная будущая таксономия не используются.

## Контракт признаков и целей

`asof_panel(panel, origin)` сначала ограничивает каталог ID, встреченными в sales не позднее **данного внутреннего origin**, затем возвращает полный декартов продукт только этих warehouse/article, массивы истории и даты до origin включительно. Сохраняется исходное допущение экспорта: отсутствующая продажа допустимой пары означает ноль, отсутствующий остаток — NaN. Наблюдение самой пары ранее не обязательно, если оба ID уже известны. Каталог и порядок активных пар определяются известными строковыми идентификаторами.

`safe_snapshot` вычисляет исходные статистики на этой уменьшенной панели. Средние warehouse/article не получают нулевое дополнение будущими ID. Строковые идентичности кодируются SHA-256 с фиксированными namespace, остаток по модулю `2**20-1`, dtype signed int32, без зависимости от будущего полного каталога или меняющегося локального порядкового номера. Коллизии проверяются среди доступных ID и приводят к ошибке; скрытое разрешение коллизий, зависящее от будущего, отсутствует. После исходного float32 snapshot столбцы категорий перезаписываются **int32**. Среди проверенных реальных активных каталогов коллизий не найдено. Ограничение пространства хеша введено после allocation failure LightGBM до появления прогнозов/метрик; причина и границы исправления описаны в `catalog_audit/encoding_runtime_fix.md`. Конечность пространства означает возможность коллизий на иных ID; обработка — явный отказ, не изменение кодов уже известных ID.

Helper возвращает позиции активных пар в исходной выходной сетке. Для обучающей цели caller использует `panel.y[origin+horizon, positions]`, проверив `origin+horizon <= cutoff`. Так ограничение цели определяется внешним cutoff, а признаки и состав строк — внутренним origin. Для weekly/article обучения тот же внутренний контракт должен применяться до агрегации; нельзя агрегировать полный будущий каталог, а затем фильтровать готовые признаки. Caller отвечает за сохранение int32 categorical columns при сборке features и за запись активных ID в metadata.

## Выходной каталог и холодный старт

`expand_to_output` проецирует прогнозы известных ID в фиксированную сетку; неизвестные на момент прогноза ID получают **0**. Итоговый контракт сохраняет 64×8789 значений. Полный output catalog нужен для покрытия формы выдачи и расчёта метрик, его позиции не становятся признаками, весами или обучающими строками. Итоговые метрики следует считать по полному truth, включая спрос будущих ID: сужение truth до survivors изменило бы задачу.

## Исполнимая проверка и границы

Команды из корня проекта:

```powershell
.\.venv\Scripts\python.exe -X utf8 integration/catalog_audit/verify_provenance.py
.\.venv\Scripts\python.exe -m pytest integration/test_catalog_policy.py -q
```

Результат: **6 passed**, обучения не запускались. Проверены добавление будущих article/warehouse с изменением лексикографического порядка, точное равенство исторических features и активного каталога после такого добавления, стабильность categorical codes между origins, отсечение ID, известных лишь на внешнем cutoff, нулевой fallback, реальная полная сетка 8789, отклонение неверных forecast/mapping. Raw first-observed независимо воспроизведён. Эти проверки доказывают контракт helper, а не отсутствие ошибок в любом вызывающем его training loop; последние должны проверяться отдельно вместе с их сохранёнными metadata и прогнозами. Исправленные веса и их качество нельзя выводить из старых NPZ без нового fit.
